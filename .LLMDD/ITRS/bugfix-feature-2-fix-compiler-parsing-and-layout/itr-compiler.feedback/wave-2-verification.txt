== 3. CROSS-CU ISSUES FOUND AND REPAIRED ==

REPAIR A (iteration 1, T2+T3 red — the item cu-002 handed off):
After cu-002's splitter ran, any synopsis-less batch with inline sections
became "new-schema" and Compile's validateSynopsis threw
"SYNOPSIS is missing" before any write. That broke feature tests T2
(bug-2 minimal repro) and T3 (feat-1 batch.json, which is a top-level
array with no synopsis key) — both must exit 0 per bugfix-feature-2
criteria 3-4, while Feat1ValidationTest "should fail naming MAX_ATTEMPTS
when synopsis is absent (T3)" pins the opposite for a batch that supplies
an explicit "components" object.

Resolution (no design change, satisfies both specs):
- validateSynopsis is now self-gating: with synopsis data present it
  validates the content as before; with no synopsis data it only fails
  when some regular CU carries component keys NOT explained by inline
  content sections — i.e. keys that came from an explicit "components"
  object (feat-1 schema opt-in, criteria 9-10). Split-derived-only
  batches and legacy batches are exempt.
- Explicit-vs-split is decided by CU.contentSectionKeys(content), which
  uses the exact same label list the JSON splitter uses.

REPAIR B (iteration 1, wave-1 watch item 2 — splitter/detector agreement):
RequiredPartsValidation re-scanned content with a second, more generous
detector (markdown headers + a mid-line `key.itr` substring check) and
unioned it into effectiveComponentKeys. That let validation pass a CU the
writer would emit as a blob: a prose CU mentioning COORDINATES.itr /
REQUIREMENTS.itr / IMPLEMENTATION_STEPS.itr / ACCEPTANCE.itr compiled
exit 0 and wrote cu-<id>/cu-<id>.itr inside a new-schema batch
(pass-with-blob disagreement), and partial key sets could be "passed" while
only some component files were written.

Resolution: effectiveComponentKeys now reads exactly cu.components — the
map FileSystem.write branches on and writes one file per key. Split-derived
keys need no separate detection because cu-002 already puts them in
cu.components; explicit keys are parsed by cu-001's parser. The content
re-scan (splitContentKeys, incl. the `.itr` leniency) is deleted.
Validation and writer can no longer disagree by construction.
