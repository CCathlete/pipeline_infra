3. CROSS-CU CONFLICT FOUND AND REPAIRED (cu-002)
------------------------------------------------
Problem: cu-002 added feat-1 enforcement in Compile.execute that ran
unconditionally -- including single-CU/raw mode and legacy/old-schema batches.
It rejected every regular CU lacking all four components and every batch
lacking a synopsis. That contradicts:
  - feature spec criterion 11: "A component-less legacy CU keeps exactly one
    <cu-id>.itr frame inside its own folder";
  - cu-003 STEP 4: old layout behaviour unchanged for component-less batches;
  - cu-004 ACCEPTANCE: "old-schema batches still compile unchanged";
  - existing contract tests: CompileTest (raw + legacy JSON/YAML),
    BatchJSONWriteTest, SingleCUWriteTest.
Observed before repair: 5 CompileTest failures (raw content, JSON batch, YAML
batch, empty input, DTR-coordinate raw) and the integration suites fail too.

Repair (implementation only -- NO test file was modified, per RULE.VER.REPAIR):
  - Compile.scala: feat-1 enforcement now runs only in batch mode AND only for
    "new-schema" batches -- i.e. when a synopsis is defined or at least one
    regular CU carries components. Legacy batches and raw single-CU mode are
    exempt.
  - RequiredPartsValidation.validateComponents: only regular CUs that actually
    carry at least one component are required to carry all four; a fully
    component-less regular CU is a legacy CU and is exempt (criterion 11).
  - validateBatch / validateForSingleCU signatures, ARCH/LEGEND required-parts
    logic, override-file exemption, exception type (IllegalStateException) and
    fail-fast-before-writes position are all unchanged.
